# UI guidance (read before any `ui/` change)

Covers the breadcrumb comment standard, theming, edge-fade masks, and Lucide icons. Read this before touching anything under `ui/` or markup in `index.html`.

## Breadcrumb comment standard (every `ui/` file)

The codebase relies on a **breadcrumb comment system**: every file opens with a short header that says what it is and how it connects to its neighbours, so a coding agent can map the app *without reading every file*. Keep it consistent.

### Every file's top block

1. **`'use strict';`** first (for ES modules) — unchanged.
2. **A purpose header** — one line `Title — what this file is.`, then 1–4 lines of *what lives here / how it fits*, naming the key sibling files as **breadcrumbs**. Prefer the purpose header to be the **first** comment in the file.
3. **Breadcrumbs must use current, real paths.** Write them as repo-relative paths (`ui/main-panel/wiki/wiki.html`, `app/api/wiki.py`, `ui/shared/js/state.js`). After any move/rename, fix the pointers — a breadcrumb to a path that no longer exists is worse than none. (This whole sweep existed because the page restructure left dozens of pointers aimed at the old `ui/js/…`, `ui/css/…`, `ui/<page>.html` locations.)
4. The shared **`COLOR SCHEME →`** reminder, when a styling file needs it, sits **below** the purpose header — it never replaces "what is this file".

A folder with many modules should carry a `README.md` module map (see `ui/chat-side-panel/js/README.md`); file headers can then be one line plus "module map: <that README>".

### Robustness markers — tell the next agent what to remove and what to keep

So that an agent prunes confidently *and* doesn't delete things that only look dead:

- **`REMOVE-WHEN: <condition>`** — this code's lifetime is tied to a feature; delete it when the condition holds. (e.g. a drop-in page module: `REMOVE-WHEN: the Browser page is dropped from the page catalog`.)
- **`DEACTIVATED (intentional): <why>`** / **`DEACTIVATED (orphaned): <why>`** — code that is currently inactive but kept on purpose (or left behind by a half-done move). Pair it with a `REMOVE-WHEN` if it should eventually go. (e.g. the `.s2a-*` send-to-agent CSS in `ui/shared/css/app1.css`, whose JS handler was removed in the restructure.)
- **`KEEP (intentional): <why>`** — a file/block that *looks* redundant or unused but must not be deleted or de-duplicated. (e.g. `ui/diagnostics.html` and `ui/test_interface.html` — deliberate self-contained standalone pages.)

If you confirm a feature is gone, **remove its dead code** rather than leaving it silently; if you're unsure, mark it with one of the above so the decision is explicit and grep-able.

### Exemptions (leave their banner style as-is)

- **Background plugins** (`ui/background/**`) — self-contained `/* ===== */` banners; deleting the folder removes the feature.
- **The two SISTER-PANEL ability tables** (`ui/shared/js/{admin,agent}-ability-table.js`) — keep the `// ╔══╗ SISTER-PANEL: AGENT-ABILITY-TABLE` banner.
- **The splash subsystem and `cursor-effects.js`** — their own banner style.
- **Vendored/minified files** (e.g. `ui/splash/splash-page/js/lenis.min.js`) — never edit; record provenance in the folder README, not inside the minified blob.

> **Syntax vs. content.** This standard governs *content and order*. Header **syntax** (JSDoc `/** */` vs. `//` line blocks) and `"use strict"` vs `'use strict'` quoting are still mixed across `ui/`; a separate normalization pass unifies those.

## Theming — one palette drives the whole app (dark AND light)

Every new UI feature in `ui/` (and any markup in `index.html`) **must be tested and visually correct in both dark mode and light mode** before it is considered done. The app toggles between themes via `body.light-mode`; all theme colours live as CSS variables in **`ui/shared/css/design-system.css`**.

### The palette is the single source of truth — re-theming is a one-file edit

`design-system.css` is structured in **layers**, and the whole app (every panel, button, bubble, scrollbar, **and** the animated starfield background) is wired to it:

1. **PALETTE block (the edit-here zone)** — at the top of **both** the `:root` (dark) and `body.light-mode` (light) blocks. Holds the raw colours: brand hue, purple, status hues, neutral surfaces, and the ambient page-glow colour. To switch the whole scheme (e.g. peach → green), you change **only** the raw values in these two blocks — nowhere else. (Animated-background tokens live with each background plugin under `ui/background/<id>/` but reference this palette — see below.)
2. **Each hue has an `-rgb` triple** (e.g. `--brand-rgb: 125, 207, 255`). Build any opacity from it with `rgba(var(--brand-rgb), 0.2)` — that way a hue is authored **once** per theme and every tint derives from it.
3. **Derived/semantic tokens (wiring — don't edit to re-theme)** — `--accent`, `--accent-soft`, `--user-bubble-bg`, the `--shadow-*` set, etc. are all defined as `var(--brand)` / `rgba(var(--brand-rgb), a)` formulas. They are declared in **both** theme blocks (CSS resolves `var()` per-element, so a token referencing the palette must be re-declared under `body.light-mode` for it to pick up the light palette — this is intentional duplication of the *formula*, not the colour). Alphas may differ between the two blocks on purpose (a tint needs more opacity over a bright surface).

So: dark and light are **independent palettes** (the factory default is **Ocean** in light mode and **Amber** in dark mode; the **Mono** preset is the neutral grey/black-and-white scheme; other selectable presets re-theme to Forest, Grape, Rose, etc.) — change either block's raw values to re-skin that theme.

### The animated background reads the palette too (now a plugin system)

The full-screen animated background is **pluggable** — see `ui/background/README.md`. Each background is a self-contained drop-in folder `ui/background/<id>/` (`<id>.json` descriptor + `<id>.js` renderer + `<id>.css` tokens); the engine in `ui/background/_engine/` owns the single `<genui>` and loads whichever background the admin chose for the active theme. The admin picks one **per theme** (App Settings → **Appearance**), saved to app settings and delivered to every visitor via the public `GET /api/v1/auth/ui-config`. The built-in **None** = plain themed background.

**Tokens live with the plugin, derived from the palette.** A background is **not** painted with hard-coded colours — its `<id>.js` reads its own `--*` tokens from the computed style of `body` (with JS fallbacks only for the pre-stylesheet frame) and re-reads on theme flip. Those tokens are defined in the plugin's own `<id>.css` (e.g. Stargaze's `--sg-*` are in `ui/background/stargaze/stargaze.css`, **not** `design-system.css`), but they **reference the central palette** (`var(--brand-rgb)`, etc.) where possible so a scheme swap still flows. This keeps each background self-contained: delete its folder and the renderer, its CSS and its tokens all go together, and it disappears from the Appearance selector (a removed background falls back to Stargaze).

The cursor glow and card spotlights are **not** part of a background — they live in `ui/shared/js/cursor-effects.js` and run for every background, including None.

**Rules:**

1. **Never hard-code a brand/scheme colour** (hex or rgb) in CSS, inline styles, HTML attributes, or JS string templates. Reference the token. CSS variables resolve inside inline styles too, so JS can use `el.style.background = 'rgba(var(--brand-rgb),0.12)'` or `style="color:var(--brand)"`.
   - Backgrounds: `var(--bg-0)`, `var(--bg-1)`, `var(--bg-2)`, `var(--bg-elev)`, `var(--bg-elev-2)`, `var(--bg-tint)`
   - Borders: `var(--border)`, `var(--border-soft)`, `var(--border-strong)` (colour) — and **write the width as `var(--border-width)`, never a literal `1px`** (see "Global border control" below)
   - Text: `var(--fg-1)`, `var(--fg-2)`, `var(--fg-3)`, `var(--fg-4)`
   - Brand / semantic: `var(--accent)` (= `var(--brand)`), `var(--accent-soft/-mid/-line)`, `var(--purple)`, `var(--success)`, `var(--warning)`, `var(--danger)`; for custom opacities use `rgba(var(--brand-rgb) / --purple-rgb / --success-rgb / ..., a)`.
2. **Never write `var(--foo, #darkhex)` fallbacks.** A literal dark hex as a fallback silently breaks light mode. If the variable doesn't exist, add it to the palette.
3. **A new theme-sensitive colour goes in the PALETTE block of BOTH theme blocks** (with an `-rgb` triple if it'll ever need an alpha) — never sprinkled through feature code.
4. **Verify before pushing:** open the feature, toggle `body.light-mode`, confirm every panel/text/border is legible in both. A quick whole-app smoke-test: temporarily change `--brand`/`--brand-rgb` in one block and confirm the change cascades everywhere (including the background glow), then revert.

### Global border control (one knob for colour · thickness · on-off)

Every **neutral container / table / divider border** in the app is written as
`var(--border-width) solid var(--border)` (or `-soft` / `-strong` for the colour). That makes the whole app's structural border treatment controllable from **one place** — and there are now **three** equivalent edit surfaces, in order of friendliness:

- **App Settings → Appearance** (the UI; admin-only) — the border knob now lives inside the **combined theme panel** (see "Appearance panel" below): border thickness (Off / Thin / Medium / Thick) and the app/code fonts sit in a shared card, and the per-theme border **colour** is one of the palette swatches under each theme. Every control previews live in the admin's own window via `window.WA_APPEARANCE.setOverrides` and **auto-saves** to app settings with the shared green tick. Markup in `ui/admin-tools/app-config/app-settings/app-settings.html`; logic (`_initAppearance` / `_loadAppearance` / `_buildThemeCard`) in the sibling `.js`.
- **`data/config/app-settings.json`** (the live override the panel writes, also hand-editable) — `border_color_dark`, `border_color_light`, `border_width`, `font_sans`, `font_mono` (plus the full palette keys — see "Appearance panel") are served app-wide through the public `/api/v1/auth/ui-config` endpoint and injected at boot as CSS-variable overrides by **`ui/shared/js/appearance.js`** (mirrors the background manager). Edit the JSON, reload the page — no server restart, no CSS edit — and every visitor follows. **Exception:** adding a *brand-new* key the `AppSettings` model didn't have requires a server restart (no Python hot-reload); editing existing keys is restart-free. A **blank** value falls back to the design-system.css default for that token. (Server side: `app.admin.settings.get_appearance_config` + the `AppSettings` model.)
- **Per-theme injection (scope matters — derived tokens depend on it):** `appearance.js` emits its palette overrides as **two theme blocks** — `:root{…}` (dark) and `body.light-mode{…}` (light) — plus a separate `:root{…}` block for the theme-independent knobs (fonts, radius/shadow/ui scale). The **dark** block must land on **`:root`** because dark is the root/default theme and design-system.css declares the dark **derived** tokens (`--accent`, `--bg-1`, `--border-soft`, the brand-glow shadows, …) at `:root`, computing them from the base swatches at the **same scope**. If the dark override sat on `body:not(.light-mode)` instead (as it once did), those `:root`-scoped derived tokens would keep computing from the *un-overridden* base defaults — so the whole derived ramp (accent alias, neutral surface/border steps, status tints, brand glow) would stay **frozen on the stock cyan/blue palette in dark mode** even after a theme change. The **light** block stays on `body.light-mode` (its derived tokens are declared there too) — and design-system.css always re-declares the **full** light palette at `body.light-mode` (higher specificity than `:root`), so a dark-only override can never leak into light mode. `--border-width` is written into **both** theme blocks so "Off"/thickness wins in either mode (the old "borders off doesn't work in light mode" fix). Keep this shape: dark/default → `:root`, light → `body.light-mode`.
- **`design-system.css` PALETTE block** — the CSS defaults (`--border` / `-soft` / `-strong`, `--border-width`, `--font-sans` / `--font-mono`) that all of the above fall back to when an override is blank.

Either surface does the same three jobs:

- **Recolour** → `--border` / `--border-soft` / `--border-strong` in CSS, or `border_color_dark` / `border_color_light` in the JSON (both per-theme; the JSON drives only the main `--border`, soft/strong stay their CSS depth variants).
- **Thicken / thin** → `--border-width` in CSS, or `border_width` in the JSON (default `1px`).
- **Turn ALL borders off** → `--border-width: 0` (CSS) or `"border_width": "0"` (JSON).

Rules when adding UI:

1. **A neutral border's width is `var(--border-width)`, not a literal px.** A hard-coded `1px` opts that border out of the thickness/off control — don't do it for structural borders.
2. **Accent/semantic borders are deliberately NOT wired to this** — focus rings, `:hover`/`.active` highlights, error/drag (`dashed`) outlines, status borders, and **loading-spinner rings** keep their own literal width and accent colour, so they survive a "borders off" and stay meaningful. Leave those as-is.
3. **Documented colour-only exceptions:** the floating-glass surfaces re-skinned in `index.css` (`#main-panel`, the `#chat-panel .chat-pill` family, chat bubbles, `#chat-header` divider) keep a translucent `color-mix(... currentColor ...)` border *colour* (it auto-adapts to the theme) but **do** read `var(--border-width)`, so they still thicken and turn off with the global knob — they just don't follow the `--border` colour. The admin file-tree's `--files-border` / `--files-border-strong` tokens are redefined to `var(--border)` / `var(--border-strong)`, so the file tree follows the global colour too. The terminal overlay (self-contained dark surface) and the agent-loop visualizer keep their own borders, same as the other palette exceptions above.

### Known self-contained palette exceptions (NOT driven by the global scheme)

A few surfaces deliberately own their colours and will **not** follow a palette re-theme. If you do a full re-skin, edit these too:

- **The agent-loop visualizer** — `ui/main-panel/agents/agent-loop/loop-visual.css` (+ `js/loop.js`, `js/loop-diagram.js`) has its own complete dark **and** light palette, including many bespoke neutral shades with no design-system equivalent and a distinct light-mode blue/green scheme. Left as a self-contained island.
- **The terminal ANSI palette** — `ui/shared/js/terminal.js` defines conventional xterm ANSI colours; these are terminal-standard, not app brand.
- **The tutorial badge's light mode** — `ui/tutorials/tutorial.css` uses a deliberate blue (`#2563eb`) for the light-mode badge (its dark side follows `--brand`).
- **Animated backgrounds** — each `ui/background/<id>/<id>.css` owns its colour tokens. They reference the palette where possible (so a brand swap mostly flows), but bespoke values (e.g. Stargaze's nebula triples) live in the plugin folder, not `design-system.css`. For a full re-skin, edit each background's CSS too.

### The Appearance panel — one combined theme editor (palette · background · fonts)

App Settings → **Appearance** is **one** group (the old separate "Appearance" background selector and "Borders & Fonts" picker were merged). It is a **two-row expandable table** built on the shared ability-table component (`.ac-list` → two `.ac-row`s, **Light** and **Dark**, each with an `.ac-ability-row` head + an `.ac-ability-body` that opens like an ability row), plus a shared, theme-independent card below. The group's **header bar** (the sticky `.ac-category-summary` with the palette icon + "Design") also carries a compact **live theme switch** on its right edge (`.ac-theme-switch` — Light · Dark · System): the SAME per-browser toggle as the user-menu dropdown (it reuses `setTheme`/`highlightThemeOption` exported from `ui/shared/js/user-panel.js`, so both stay in sync; wired by `_initThemeSwitch` in `app-settings.js`). It is `position:absolute` so it never grows the header's height. This flips *which* theme you're viewing — distinct from the Light/Dark rows below, which edit each theme's colours.

- **Each theme row** expands to reveal: a strip of **one-click preset chips** (`_PRESETS` — Mono (neutral greyscale) / Amber / Ocean / Forest / Grape / Rose; the factory default = Ocean light + Amber dark), the **animated-background select**, and the **full palette as colour swatches** (accent, secondary, the three status hues, the surface shades, text, muted text, ambient glow, border, **plus User bubble + Agent bubble + Chat pill**). The swatch **order + which CSS token each drives is the single source of truth in `ui/shared/js/appearance.js`** (`window.WA_APPEARANCE.tokens`); the panel only attaches a friendly label + icon + flags per token (`_TOKEN_META` in `app-settings.js`). The rows expand via the shared `_wireBootRow` (clicks on a control inside the body never toggle the row).
  - **Presets re-theme the WHOLE UI, not just the accent.** Each `_PRESETS` entry carries its own **neutral wash** (`surface_bg`/`surface_panel`/`surface_tint`/`text`/`text_muted`/`border_color`) per theme — a subtle hue-tinted set — so Forest/Grape/Ocean stop looking peachy.
  - **Clicking a theme is a COMPLETE RESET of that mode** (`_applyPreset`). It rewrites *every* palette token: the theme's explicit value where it has one, else **blank** for `follow` tokens (bubbles → back to tracking the theme) and the **design default** for everything else — wiping any per-swatch colour, opacity, or bubble override. Both the swatch and its opacity slider are re-synced.
  - **"Add theme" + custom themes.** The `+ Add theme` button (`_addCustomTheme`) snapshots the CURRENT palette of **both** modes (`_snapshotTheme` — every token incl. opacity `#rrggbbaa` and bubble state) into a named entry appended to `_customThemes`, which renders as an extra chip (with a delete `×`) beside the built-ins. Custom themes persist as a **JSON array string** in the `custom_themes` `AppSettings` field (admin-only; NOT in `ui-config` — visitors only need the resolved palette). They apply / reset exactly like built-in presets.
  - **`_TOKEN_META` flags:** `alpha:true` adds an **opacity slider** beside the colour swatch (on the surfaces + border + both bubbles + the chat pill); the colour + slider combine into a `#rrggbbaa` value. `follow:true` (the two bubbles **and the chat pill**) means the token defaults to **blank** (= follow the theme-derived default) and is skipped by presets; set its swatch to pin it. A bubble/pill at 0 opacity = text with no background. **Bubble/pill-bg gotcha:** the theme-following default is derived at the **target element** in `index.css` (`--chat-bubble-bg: var(--user-bubble-bg, color-mix(in oklab, var(--bg-elev) …)))`, and `#chat-panel .chat-pill { background: var(--chat-pill-bg, color-mix(in oklab, var(--bg-elev) …)) }`), *not* as a global `--user-bubble-bg`/`--agent-bubble-bg`/`--chat-pill-bg` token at `:root`. Those override tokens are left **unset** unless a swatch pins them. Reason: the Appearance override of `--bg-elev` lands on `<body>`, so a `color-mix(var(--bg-elev))` evaluated at `:root` would bake in the pre-theme panel colour — the cause of the "peachy bubbles in every theme" bug. Resolving it at the element (inside `<body>`) picks up the live themed panel. **All three (user bubble, agent bubble, chat pill) share the identical `color-mix(--bg-elev 82%/85%)` default**, so they match out of the box and can each be pinned independently. The chat-pill default + override is scoped to `#chat-panel .chat-pill` only (resting + focus + drag) — the other floating-glass pills (ability-search / genui / browser) keep their lighter shared glass skin.
- **The shared card** holds border thickness + the two fonts (these are not per-theme).
- **Every control auto-saves** per theme with the shared `.agents-autosave-check` green tick (same mechanic as the ability tables / model table — `_markCheckSaving` / `_flashCheck`), and previews live via `WA_APPEARANCE.setOverrides` (palette/border/font) or `WA_BG.setChoice` (background). The presets, swatches and background selects are **built in JS** by `_buildThemeCard` into each row's `.ac-ability-body`, so the HTML stays small (just the two row shells).

**JSON-only style knobs (no UI control — edit `data/config/app-settings.json`).** Five *theme-independent* knobs are deliberately **not** in the panel; they're applied app-wide by `appearance.js` exactly like the palette, but you change them only by editing the JSON (or POSTing to `/admin/settings/app`): `radius_scale` (corner roundness × — design-system radii are `calc(<px> * var(--radius-scale))`), `shadow_strength` (drop-shadow depth × — shadow alphas are `calc(<a> * var(--shadow-strength))`; the accent `--shadow-glow` is left unscaled), `ui_scale` (whole-UI `zoom` on `<body>` via `--ui-scale`), `reduce_motion` (`"on"` → `appearance.js` injects a global animation/transition-collapsing rule), and `cursor_glow` (`"off"` → injects `#cursor-glow{display:none}`). Each defaults to a no-op (`"1"` / `"off"` / `"on"`). To add another such knob: a CSS hook in `design-system.css` (a `calc()` on a `--var`, or a `zoom`), a default in `appearance.js` DEFAULTS + the apply logic, and the field in `_DEFAULT_APPEARANCE` + `AppSettings` + `UiConfigResponse`.

**Not every appearance-pipeline key is a theme/CSS knob — nor JSON-only.** The RAM media-cache keys **`media_cache_enabled`** (`"on"`/`"off"`) and **`media_cache_budget_mb`** ride this exact pipeline (DEFAULTS in `appearance.js` → `_DEFAULT_APPEARANCE` + `AppSettings` + `UiConfigResponse` → injected at boot), but instead of emitting CSS they call `window.WA_MEDIA_CACHE.configure(...)` to size the in-browser attachment/thumbnail cache (`ui/shared/js/media-cache.js`). They are the first such keys with their **own admin UI outside the Appearance panel** — the **Memory Cache (RAM)** row in App Config → **Data Settings** (`ui/admin-tools/app-config/data-settings/media-cache-settings.js`), which saves via `POST /admin/settings/app` and previews live through `WA_APPEARANCE.setOverrides`. So a control that writes an appearance-config key can live wherever it fits functionally; the delivery pipeline is the same. The cache is a **volatile speed layer** (LRU-evicted under a byte budget, never a place of record) sitting in front of whichever attachment store actually holds the bytes.

**Chat-composer geometry knobs (also JSON-only).** The whole look of the **tall chat composer** (`#chat-input-row`) is exposed the same way — ten `chat_pill_*` keys, each a plain CSS length, injected by `appearance.js` as the matching `--chat-pill-*` variable and consumed by the `CHAT-PILL-VARS` block in `app1.css` (each `var()` carries a fallback equal to the JSON default, so the look holds before the override lands). The knobs: `chat_pill_max_width` (width cap; the composer is centred under it), `chat_pill_radius` (corner roundness), `chat_pill_padding` (outer padding shorthand), `chat_pill_min_height` / `chat_pill_max_height` (resting + grow-cap text-area height), `chat_pill_font_size` (input + placeholder), and the four button knobs `chat_pill_attach_size` / `chat_pill_attach_icon` (attach `+` box + glyph) and `chat_pill_button_size` / `chat_pill_button_icon` (mic / send box + glyph). They drive **only** the tall composer — the compact 1-line bars (search/builder/genui/browser) keep their fixed sizing via the more-specific `.chat-pill-1line *` rules. Wiring is table-driven (`CHAT_PILL_KNOBS` in `appearance.js`), so adding one is a row there + a `var()` in `app1.css` + the field in `_DEFAULT_APPEARANCE` + `AppSettings` + `UiConfigResponse`.

**Chat panel layout (UI-exposed, in the Design group).** Two app-wide keys are exposed as standard config rows at the bottom of the App Settings **Design** table (`#ac-design-list`, alongside the Startup & Boot rows) and ride the same `appearance.js` → `/api/v1/auth/ui-config` pipeline: `chat_position` (`"right"` default | `"left"`) and `chat_default_visible` (`"visible"` default | `"hidden"`). `chat_position: "left"` makes `appearance.js` inject `@media (min-width:801px){#stage{flex-direction:row-reverse}}`, flipping the desktop split so the chat sits left of the main panel; `chatResize.js` reads the live geometry (chat-vs-handle position) to keep drag-to-resize working on either side, so no setting is read there. `chat_default_visible` only **seeds the first-visit desktop default** — `index.html`'s pre-paint block + `window.__chatVisibilityDefault()` read it off the cached `wa_appearance` blob; once a visitor toggles the chat their own per-browser `chatPanelVisible` wins. Both selects are wired in `app-settings.js` `_wireChatLayout` (save + green tick via `_saveAppearance`, live preview via `_previewAppearance`) and loaded in `_loadAppearance`; fields live in `_DEFAULT_APPEARANCE` + `AppSettings` + `UiConfigResponse` + `appearance.js` DEFAULTS.

**How a swatch reaches the screen:** each palette token is stored per theme as `data/config/app-settings.json` keys `<base>_dark` / `<base>_light` (the border's are the historical `border_color_dark/_light`), defaulted server-side in `app.admin.settings._DEFAULT_APPEARANCE` (mirror of the two `design-system.css` palette blocks) and the matching `AppSettings` fields, served via `/api/v1/auth/ui-config`, and injected at boot by `appearance.js`. For any hue with translucent tints, `appearance.js` **derives the `-rgb` triple from the chosen hex** and writes both, so changing one swatch moves the solid colour *and* every `rgba(var(--x-rgb), a)` tint. Tokens cover `--brand`(+`-strong`/`-rgb`), `--purple`(+…), `--success`/`--warning`/`--danger`(+`-rgb`), `--bg-0`/`--bg-elev`/`--bg-tint`, `--fg-1`/`--fg-3`, `--ambient-2-rgb`, `--border`, the bubbles `--user-bubble-bg`/`--agent-bubble-bg`, and the chat composer pill `--chat-pill-bg`.

**Opacity (surfaces + bubbles).** A stored value may be `#rrggbb` **or** `#rrggbbaa` — the trailing `aa` is opacity. `appearance.js`'s `parseColor` reads either; `pushToken` emits the token as `rgba(r, g, b, a)` when `a < 1` (else a solid hex), while the `-rgb` triple stays alpha-free so existing `rgba(var(--x-rgb), a)` tints are unaffected. The panel stores/loads the alpha with the colour via `_combineColor` / `_splitColor`. Because surfaces feed the `color-mix` neutral ramp, a translucent surface yields a translucent ramp — by design (e.g. a see-through panel shows the animated background through every derived step).

**The graduated neutrals follow the swatches too — by derivation, not by a separate swatch.** `--bg-1`, `--bg-2`, `--bg-elev-2`, `--bg-tint-2`, `--border-soft`, `--border-strong`, `--fg-2` and `--fg-4` are **not** their own editable values; in `design-system.css` (both theme blocks) each is a `color-mix(in oklab, …)` of a swatch anchor (`--bg-0`/`--bg-elev`/`--bg-tint`/`--border`/`--fg-1`/`--fg-3`), on the rule *"an elevated surface moves a little toward the text colour"* (true in both themes). Because the mix references the swatch `var()`, editing a swatch flows through the **whole neutral ramp live**, not just the three raw surface anchors. So there are only **6 raw neutral knobs** (Background = `--bg-0`, Panel = `--bg-elev`, Tint = `--bg-tint`, Border = `--border`, Text = `--fg-1`, Muted = `--fg-3`) and every other neutral step is a function of them. **When you add a new neutral step, derive it the same way** — never hard-code a fixed neutral hex, or it will be the one surface that ignores the swatches. (This is why feature CSS must reference `var(--bg-*)`/`var(--fg-*)`/`var(--border*)` and never a raw neutral hex in *either* theme — a hard-coded light **or** dark neutral silently opts that surface out of its swatch.)

**Adding a palette token to the editor** = add it in **three mirrored places**: the `TOKENS` map in `appearance.js` (drives injection + the swatch order), `_DEFAULT_APPEARANCE` + the `AppSettings` field in `app/admin/settings.py` (persistence + the public endpoint), and a label/icon in the shared `TOKEN_META` in **`ui/shared/js/appearance-editor.js`** (NOT in `app-settings.js` — that file now imports `TOKEN_META`/`APP_DEFAULTS`/`PRESETS`/`FOLLOW_ALPHA` + the colour helpers from `appearance-editor.js` so the admin and per-user editors share one source). No HTML edit (swatches are built from the token list). A brand-new key needs a **server restart** to register on the `AppSettings` model.

### Per-user themes (each user's own appearance, layered on the global one)

The Appearance panel carries one admin switch — **"Allow per-user themes"** (`allow_user_appearance`, off by default; the toggle row sits right under the Light/Dark rows). When **on**, every signed-in user gets a **"My appearance"** editor on their **Manage Account** page (`ui/shared/js/account.js`) — the *same* Light/Dark theme table (presets, background, the full swatch palette, fonts, border) plus a **"Reset my theme"** button. It is built by `ui/shared/js/appearance-me.js`, which imports the shared definitions from `appearance-editor.js` and mirrors the admin `_buildThemeCard` structure (change one → mirror the other).

- **Storage = the user's profile.** A sparse JSON patch (only the tokens that user changed) is kept in `user_profiles.appearance` (migration 031 / the in-code "Migration 031" block in `app/db/local.py`; DB helpers `get_user_appearance` / `merge_user_appearance` / `set_user_appearance`). Self-service via **`/api/v1/auth/me/appearance`** (GET reads `{allow, overrides}`; PUT merges a patch — a blank value clears that token; DELETE resets all).
- **Application = one seam, no `appearance.js` change.** `GET /api/v1/auth/ui-config` already resolves the caller; when the flag is on and the caller is a signed-in user it layers their saved overrides on top of the global appearance (and re-validates their background) before responding, so the boot-time applier just paints an already-personalised theme. **Fall back to global:** any token the user hasn't set keeps the global value. When the flag is off the merge is skipped and the editor is hidden, so saved personal themes are simply ignored (not lost). The per-user editor reads the installed-background catalog from the public **`/api/v1/auth/backgrounds`** (the non-admin sibling of `/admin/settings/backgrounds`).

## Edge fades over a dynamic/themed background — mask, never a colour

When a scrolling strip (a horizontal tab carousel, a content list, etc.) needs its edges to **fade out** so the content doesn't cut off abruptly, **fade the content with a CSS alpha mask — never paint a coloured gradient to fake it.**

**Why this is a hard rule here:** several surfaces in this app sit over a background that is **not a static colour** — most notably the **live stargaze genui** (`ui/background/stargaze/stargaze.js`), which continuously redraws a warm peach (light) / nebula (dark) glow that shifts with theme and pointer position. The page base colour (`#faf5ee` light / `#07070c` dark, set in `index.css`) is *not* what you actually see there. So any edge fade implemented as `linear-gradient(..., <some colour>, transparent)` will be a guessed static colour that can never match the moving background — it shows up as a lighter/whiter rectangle. A **mask** paints no colour at all (alpha only): it fades the *content* to transparent and lets the real background — glow and all — show straight through, matching automatically in both themes and even while the genui animates.

**The pattern (two ingredients):**

1. **Transparent buttons/affordances** (e.g. carousel chevrons) positioned over the edge — `background: none`, glyph colour from a design-system var so it tracks the theme.
2. **A `-webkit-mask-image` / `mask-image` linear-gradient on the *scroller itself*** that goes `transparent → #000` over the fade width at the edge, applied **only on the side(s) that can still scroll**, toggled by the scroll-state classes the carousel JS already maintains.

**Canonical implementations to copy:**

| Location | Selector |
|----------|----------|
| Agent card carousel (origin of the technique) | `.agent-card-tabs` / `.agent-card-tabs-chev` in `ui/main-panel/agents/agents.css` |
| Main header tab strip | `#main-tabs` "Masked edge-fade carousel" block in `ui/shared/css/design-system.css` |

Both blocks carry a full explanatory comment. The `:has()` per-side selectors used for the header need a modern browser (Chrome 105+, which the app targets); if you ever need older support, toggle the mask via a JS class on the scroller instead.

## Pinned rounded scroll corners — mask, reveal the background

When a **scroll viewport** should show **rounded corners that stay put while the content scrolls** (they don't scroll away), round it with an alpha **mask** — not `border-radius` alone, and not by shrinking the viewport. This is the same "paint no colour, reveal what's behind" idea as the edge fade above, and it solves three problems at once:

- **The rounding stays pinned to the viewport.** A mask paints the scroller's *fixed* box, so the rounded corners sit still while rows scroll underneath.
- **The scrollbar stays at the far edge and the whole width still scrolls.** We do **not** clip the viewport narrower — the scroller stays full-width; we only knock the four corners transparent.
- **The corners are theme-correct.** The mask reveals the panel's **own** background (gradient, glow, the animated genui) through the corners, so they match in light/dark automatically — never a guessed corner colour.

**The reusable class:** `.rounded-scroll-corners` in `ui/shared/css/design-system.css` (right after the edge-fade carousel block). Add it to any `overflow:auto` scroller and its four corners round, pinned. Two custom-property knobs:

| Knob | Meaning | Default |
|------|---------|---------|
| `--rsc-r` | corner radius | `--r-lg` |
| `--rsc-side` | per-side inset to a **centred column** (keeps that side strip opaque, so a scrollbar / centring gutter stays visible) | `0` (full-width rounding) |

It builds an opaque rounded rectangle as a `mask-composite: add` **union** (two side strips + a horizontal bar + a vertical bar + four inset corner discs) and knocks out only the four outer-corner slivers → normal **outward** (convex) rounding. A `0` radius makes the whole mask a full-opaque no-op, which is how a shared scroller can carry the class but stay un-rounded until switched on.

**Reference implementation — the centred-column variant:** App Settings (`#app-config-content`, gated to its tab in `ui/shared/css/app3.css`). That scroller is shared by all 10 App-Config tabs, so the class is left **inert** by default (`--rsc-r: 0`) and switched on only while one of the standard centred-column sections is active — **App Settings, Agent Settings, and Data Settings** (each an `ac-stickynav` section with 750px-capped `.ac-list` tables) — where it's fed a **computed** `--rsc-side` so the rounding hugs the 750px column (not the full panel) and tracks the width down to the scrollbar-gutter floor. (App/Agent Settings have a page-assistant pill below the scroller; Data Settings has none, so its rounded bottom corners pin to the panel floor instead of above a pill.) The width is resolved with **container-query units** (`100cqw`) off a non-scrolling wrapper (`#app-config-scroll-wrap`, `container-type: inline-size`) that hosts the column math — the wrapper exists only to be that query container. Copy that wrapper-plus-`cqw` pattern only when you need the rounding inset to a centred column; for plain full-width rounded corners just add the class and (optionally) set `--rsc-r`.

## Mobile soft keyboard — `body.kb-open` hides bottom clutter off a focused field

On a touch device, opening the on-screen keyboard shrinks the **visual** viewport (the layout viewport / `window.innerHeight` stays put). The viewport tracker in `index.html` (the same IIFE that drives `--app-height`) uses that gap to flag the keyboard: when, on a **mobile-width** viewport, the visual viewport is meaningfully shorter than the layout viewport **and** an editable field holds focus, it toggles **`body.kb-open`**. The class is mobile-gated there, so desktop never sets it.

Use it to get **bottom-docked clutter out from under a focused field** while the keyboard is up. Today the App Config pages do this (`body.kb-open` rules in `ui/shared/css/app3.css`): the page-assistant **chat pills** (`#ac-pa-bar` / `#ac-as-pa-bar`) hide, and the **sticky section headings** (`.ac-stickynav .ac-category-summary`) drop from `position: sticky` to `static` so they stop stacking at the top/bottom edges and crowding the field (e.g. the Models table's "Search models…" input) — restored automatically on keyboard close. Any other page with a fixed/floating element that would sit over a focused input can react to the same class; keep the actual hiding scoped to that page's own selectors.

## Chat pills — one shared design (two sizes), and the panel layout around them

A **chat pill** is the rounded input row with an attach button, a text area, and a mic/send button (the "Chat with the agent" box, the agent-builder bar, etc.). Every pill in the app shares **one** design and **one** source of truth; it comes in **two sizes** — see "Two pill shapes" below. Individual panels only own the layout *around* the pill.

### The pill itself is a single source of truth — opt in, never restyle per-instance

All pill **geometry and behaviour** live in **one block**: the `CHAT-PILL-SYNC` comment + `.chat-pill*` rules in `ui/shared/css/app1.css`. To add or change a pill, opt in with these classes — don't re-implement the look:

- `.chat-pill` — the outer rounded container. **Base = the TALL composer** (a CSS grid: text fills the left column and spans all rows; mic/send + attach stack bottom-right). Add **`.chat-pill-1line`** to get the **compact single-line** variant instead (one centred row, ~46px). See "Two pill shapes."
- `.chat-pill-input` — the textarea/input (tall pill: ~96px resting min-height, grows to 6 lines; 1-line pill: ~38px resting, grows a little then scrolls; the native scrollbar is hidden in both).
- `.chat-pill-attach` / `.chat-pill-voice` / `.chat-pill-send` — the left attach button and the right mic/send buttons; all three share one transparent-circle icon-button style, only the glyph differs (smaller in the 1-line variant).

**State classes** (toggled by JS, styled centrally — don't hand-roll equivalents):

- `.has-text` — input has content → swaps **mic → send**.
- `.no-voice` — force send-only (e.g. the signed-out web-chat gate).
- `.thinking` — the agent is working → glow (set by `chat-activity.js`).
- `.drag-over` — file drag hovering the pill → dashed accent border.

**Geometry vs. skin — two files, on purpose.** The base block in `app1.css` defines an **opaque dark pill** plus all geometry/behaviour. The **floating-glass** pills (the web-chat pill `#chat-panel .chat-pill`, the ability-table search/chat pill `.ability-search-pill`, the Gen UI prompt bar `#genui-prompt-row`, the in-app browser pill `.browser-prompt-row`, and the App Settings page-assistant pill `#ac-pa-bar-row`) are re-skinned transparent in `ui/shared/css/index.css` (loaded last). So: **change the floating-glass look in `index.css`; change geometry/behaviour/buttons in `app1.css`.** Never fork either into a panel's own CSS. (The browser page used to fork a cramped 36px `.browser-prompt-row` / `.browser-prompt-input` override — that clipped the send button and pushed the text off the left edge; it now opts into the shared `.chat-pill-1line` variant like every other non-chat pill.)

**Known pills (all wired to the shared classes):** `#chat-input-row` (web chat — the **tall** one), `#ac-int-admin-chat-input-row` (integration admin), `.ability-search-pill` (the **hybrid search/chat pill** — mounted **above** the per-agent card's ability table, and at the **bottom** of the admin Agent Settings page; see below), `#genui-prompt-row` (Gen UI tab), `.browser-prompt-row` (in-app browser), `#ac-pa-bar-row` (the **App Settings page-assistant** — see below). All but the first carry `.chat-pill-1line`. Change the shared block → every one updates together. (The page-level agents "builder bar" `#agent-builder-bar-row` **and** the sessions-page builder bar `#sessions-builder-bar-row` were both **removed** — the sessions page is a pure data table now, no chat pill.)

**The App Settings page-assistant pill (`#ac-pa-bar-row`).** A floating "advanced chat pill" pinned to the bottom of Admin Tools → App Configuration → **App Settings** (sticks over the `#app-config-content` scroller, only while that section is active; capped to the same 750px column as the tables). (History: this pill was previously a `position:sticky` float `bottom:calc(8px-60px)`/`margin-bottom:-60px` with an `ac-stack-floor` heading stack, then briefly an opaque heading-glow "dock" — both rejected by the owner in favour of this stops-above-the-pill layout.)

### Panel layout — full-height content, the pill floats over it

Any panel that *hosts* a pill follows one layout: the **content scroller fills the panel's entire height**, and the **pill floats over its bottom edge** as an overlay. The scroller's own scrollbar must run all the way to the bottom of the panel; content scrolls *behind* the translucent pill. This is the look on the right-hand **chat panel**, and every other pill panel must match it.

> **One deliberate exception:** the **App Settings page-assistant pill** (`#ac-pa-bar`, described above) does the OPPOSITE on purpose — it's a flow sibling *below* a shrunk scroller so content stops above it and the page gradient shows around it. That was an explicit owner decision for that one pill; do not generalise it to other panels, and do not "fix" it back to the float-over pattern.

**Why it's a hard rule:** the natural mistake is to put the pill — or any control near it (a toggle, a footer) — in **normal flow below the scroller**. A flow sibling under the scroller *reserves vertical space*, which shrinks the scroller so its content and scrollbar stop short, leaving a dead gap above the pill (the page's content visibly ends near the pill's top instead of running to the bottom). That's the exact bug that made the **agents page** look wrong next to the chat panel.

**The pattern (mirror the chat panel):**

1. **One scroller fills the panel.** The panel is a flex column (`position: relative`); the scroller is `flex: 1; overflow-y: auto` with a **bottom padding** that clears the pill's height so the last items aren't hidden under it. (Chat uses ~40px and lets content scroll *behind* the glass; that translucent-overlap is intended, not a clearance bug.)
2. **The pill is an absolute overlay**, not a flow child: `position: absolute; left/right: 0; bottom: <n>; z-index` above the scroller. It does **not** occupy layout space, so the scroller stays full-height.
3. **Auxiliary controls go *inside* the scroller** as trailing content (so they scroll with everything else and disappear behind the pill), **never** as a flow sibling between the scroller and the pill — that steals height from the scroller.

**Canonical implementations to copy:**

| Panel | Full-height content | Floating pill |
|-------|---------------------|---------------|
| Chat panel (origin) | `#chat-messages` / `#chat-messages-inner` in `ui/shared/css/app1.css` | `#chat-input-area` (`position: absolute`) |
| Gen UI page | `#genui-viewport` (holds `#genui-host`, the shadow-root genui mount) in `ui/main-panel/genui/genui.css` | `#genui-footer` (`position: absolute`, page-nav + `#genui-prompt-row`) |

(The **agents page** used to be an example here — `#agents-grid` full-height with the `#agent-builder-bar` floating pill — but that footer pill was removed; the grid is still a full-height scroller, just with no floating pill over it.)

Each panel's CSS owns **only** this wrapper layout (the scroller's height/padding + the pill's absolute positioning and bottom alignment). The pill's appearance is not the panel's concern — that comes from the shared block described above.

**Two pill shapes — the chat panel is tall, everything else is one line.** There are deliberately **two** pill sizes now:

- **The chat panel pill (`#chat-input-row`) is the TALL composer** — the base `.chat-pill` block: a ~96px box whose mic/send + attach stack bottom-right and whose textarea grows up to 6 lines. Only this one pill uses it; it's the app's primary conversation box.
- **Every other pill is the COMPACT single-line bar** — add **`.chat-pill-1line`** beside `.chat-pill` on the markup. It re-lays the same three controls (attach · input · mic/send) onto one centred row at ~46px and only grows a little when the text wraps. Used by the ability-table search/chat pill, sessions builder bar, Gen UI prompt bar, in-app browser pill, and the integration-admin bar.

There is **no longer a cross-panel bottom-alignment rule.** The old `PILL-PANEL-ALIGN` machinery (the agents/genui bars computing a `calc()` bottom offset from the chat pill's footer-row stack to keep the two side-by-side pills bottoming out on the same line) has been **removed** — the chat pill is now intentionally taller than the rest, so they don't line up and aren't meant to. Don't reintroduce a computed bottom margin to match another panel. (The separate **`PILL-PANEL-LAYOUT`** rule — full-height scroller + the pill as an absolute overlay — still stands; that's unrelated to height.)

**Verify with geometry, not a screenshot** (screenshots of these panels hang on the stargaze genui): assert the scroller's bottom equals the panel's bottom (e.g. `#agents-grid`'s `getBoundingClientRect().bottom === #tab-agents`'s) so you know it's truly full-height and the pill is overlaying rather than stacked. To check a single-line pill's height, read its `.chat-pill`'s `getBoundingClientRect().height` (expect ~46px resting) and confirm the mic/send button's box sits within it. (The chat panel is hidden below ~800px width, so widen the viewport first if you need it visible — note `preview_resize` re-inits the starfield, so prefer a fresh start at a wide size.)

## Toggle-list (category + rows of options) — one shared design

Whenever a surface shows **a category/section heading followed by a vertical list of options, each option being a row with an icon, a title, and a control (usually a toggle) on one line — with a one-line description wrapping to its own full-width line below**, it must use the app's single shared "compact row list" look. This is the design on the **Admin Tools → Agent Settings → Agent Tools** panel: one bordered, rounded container holding flush rows, soft tinted background (peach in light mode / elevated dark in dark mode), 1px hairline dividers between rows, a coloured icon at left, bold title + the control on the **top line**, and a muted description on a **second full-width line beneath**. Rows sit **directly inside the one container** — never each option wrapped in its own separate card ("card-within-a-card"). That separate-cards look (individual bordered boxes per option) is the **wrong** pattern and is what currently makes the agent card's Abilities panel look out of place.

**Stacked-row layout — `icon · title · control` on top, description below.** The row is a `flex-wrap` container in which **`.ac-ability-label` is `display: contents`** — that promotes the title and description to be flex children of the *row* itself, so the **description (`flex: 0 1 100%`, `order: 1`) drops onto its own full-width line beneath the title/control line** rather than being trapped in a narrow middle column that crams on narrow screens (the old layout). The title (`.ac-ability-name`, `flex: 1`) keeps the control pushed to the right edge; the description is indented to clear the icon column (reset to flush for icon-less config rows via `:not(:has(> .ac-ability-icon))`). Two form-column variants that reuse `.ac-ability-label` as a fixed-width label — `.ac-model-cfg-row` (model configurator) and `.ac-main-panel-item` (editable page-name field) — **opt back out** by restoring `display: block`; the model-cfg-model label already declares `display: flex`. **If you add another variant that uses `.ac-ability-label` as a plain column** (not a title+description), give it its own `display` so the `display: contents` promotion doesn't dissolve its box.

**Why this is a hard rule:** these lists appear in many places. If each one carries its own styling, a single design tweak (spacing, divider, hover, light-mode tint) has to be hand-applied in every copy and they drift apart. The whole point is that *one* set of classes drives all of them, so a change made once cascades everywhere.

**Two separate patterns, don't conflate them.** There's (a) the **collapsible section header** — chevron + icon + title that opens to reveal a group — which *is* still used elsewhere on the admin pages (`.ac-category-group`, e.g. App Settings), and (b) the **compact option-row list** *inside* such a section (`.ac-abilities-compact`). A page can have the right headers but still have the **wrong content** inside them.

**Agent Settings is now one single flush table.** Its former collapsible categories (Channels, Productivity, Social Media, Marketplaces, Payments, Developer, CRM) have been folded into the *same* `#ac-abilities-compact` list as the host-ability groups — each former category is now an **expandable group row** sitting beside Administrator / Core / Web (see `_INTEGRATION_GROUPS` + `_buildIntegrationGroupShells` / `_placeIntegrationGroupCards` in `app-config.js`). The Channels category became the **Communication** group. The **Models** block is now **always visible** — it has no collapsible heading of its own (the former `#ac-cat-models` `<details>` is a plain `<div>`). Its body renders as the shared compact-table component: a 4-row **configurator table** (`.ac-list.ac-model-config`: Provider / Base URL / API Key / Model) whose fields **auto-save on change** (each shows the shared `.agents-autosave-check` green tick, same as the agent abilities table — no Save button; the former "Save" is now an **Add** button that appends the configured model to the saved list), plus a bare **Saved Models table** (`.ac-list`) of expandable rows with a leading **Default** radio column (left of the three capability columns Text / In / Out) that picks the one model the agent runs by default — picking it calls the adapter's `saveSingle`, mirroring the row up to the top-level default; only Text-capable rows are selectable. Click a row to reveal token usage + cost, lazily fetched from `GET /admin/settings/model-info`. Per-model capabilities are **detected** from the model catalog and shown as read-only `.ac-cap-badge`s — they are not hand-entered checkboxes. The legacy integration category `<details>` are emptied and hidden at runtime, not deleted from the HTML.

**The whole Models table is a shared, instantiable component — `ui/shared/js/model-table.js` (`mountModelTable(host, opts)`).** It builds all of the table markup (configurator rows + saved-models rows + the advanced/`+` action row) into a host element with instance-scoped refs (no `getElementById`), driven by an injected `adapter` (load/save/fetch). It is mounted in **two** places that must stay mirrored — banner **`SISTER-PANEL: MODEL-TABLE`** (grep it): (a) **Admin → Agent Settings → Models** (`agent-settings.js` supplies the admin adapter pointed at `/admin/settings/provider` + `/admin/settings/multi-providers`, and relocates the app-global extras — AI suggestions + "Extend default LLM to agents" — into the table's Advanced panel); and (b) the **agent card → Config tab → LLM** (`tab-config.js` supplies a per-agent adapter that reads/writes the agent's `metadata['llm_config']` blob, including its own `multi_providers` saved-model roster). The roster is **not raced** — parallel model racing was removed; the **Default** radio picks the single model the agent runs, and the chat user can switch it per conversation. Change the table once, in the component, and both update together — never fork a copy.

The **add-new-model configurator is collapsed by default** (the table carries `ac-cfg-collapsed`, which hides the four `.ac-model-cfg-row`s). The last row of the table is a bare **action row** — not clickable itself — holding two right-pinned icon buttons: an **Advanced** button (sliders icon) that expands the advanced-options body below it, and a **`+`** button that toggles the configurator open/closed. While the form is open the `+` glyph rotates to a `×` and a **square** border appears around it (only the glyph rotates — the box never becomes a diamond). Both are wired inside the component. Saved-model names truncate with the ellipsis at the **start** (`direction: rtl`) so the distinguishing version suffix stays visible, but stay **left-aligned** above the provider line (`text-align: left`).

### Canonical implementation — copy this, don't re-invent

The whole component lives in **`ui/shared/css/app3.css`** under the boxed comment **"SHARED EXPANDABLE OPTION-ROW LIST"**. Markup contract:

- **`.ac-list`** — the bordered, rounded container (the flush "table"). The container draws the hairline dividers between items (`.ac-list > * + *`), so a bare row and an expandable row line up identically. `.ac-abilities-compact` is the legacy alias of `.ac-list` and shares its rules (the Agent Tools reference still uses it).
- **`.ac-ability-row`** — one row: `.ac-ability-icon` + `.ac-ability-label` (→ `.ac-ability-name` bold + `.ac-ability-desc` muted) + optional `.ac-ability-status` + optional `.ac-ability-toggle-wrap` (the toggle) + optional `.ac-row-chevron` (only when expandable). It is a `flex-wrap` container and `.ac-ability-label` is `display: contents`, so the icon · title · control land on the **top line** and `.ac-ability-desc` wraps to its **own full-width line below** (see "Stacked-row layout" above).
- **`.ac-row`** — wraps a row + its body to make it **expandable**; JS adds `.expanded` to open it. Use `.ac-row-static` for a non-expanding item.
- **`.ac-ability-body`** — the collapsible region revealed on expand (additional info and/or config fields: OAuth, scopes, tokens…). Hidden until opened: agent-panel cards open via the wrapping `.ac-row.expanded`; admin member rows (which are *not* each wrapped in their own `.ac-row`) open via the `.ac-body-open` class the row's click handler toggles. An **empty** body is suppressed (`:empty` → `display:none`) so a settings-less, tool-less ability shows nothing extra — there is no "No additional settings" filler. Its left padding matches the member-row indent so any settings/tools line up directly under the ability.

Light-mode overrides (the peach tint) sit in the matching `body.light-mode` rules right below. The collapsible *section header* that holds a whole list (chevron + icon + title) is the separate `.ac-category-group` / `.ac-category-summary` block (see its "SHARED COLLAPSIBLE SECTION PATTERN" comment). Everything uses **design-system CSS variables** for colour (no hard-coded hex except the light-mode peach overrides) — keep it that way.

> **Restyle the toggle-list look in `app3.css` only.** Don't fork a per-page or per-panel copy. Every conformant area below reads from this single block so the whole app stays coherent. The agent card keeps its `.conn-*` class names purely as JS/behaviour hooks (their visual rules are gutted in `agents.css`); the admin integration cards are grouped into one `.ac-list` by `_groupIntegrationLists()` in `app-config.js`.

### It's not just for simple toggle rows — the row is a flexible shell

The compact table is the right home for **any "category → list of options" surface**, not only on/off toggles. The row shell (icon + name + description on the left, with the rest of the row free) accepts whatever control or affordance the option needs. Reach for it whenever options share a category, even when each option does something richer than flip a switch:

- **Toggle rows** — the default (a switch on the right). *Agent Tools, integrations.*
- **Other controls on the right** — a row's control can be a **radio**, a **dropdown/select**, a **button**, a small **number/text input**, or a **status pill / "Coming soon" badge** instead of a toggle. Same row, different right-hand element.
  - **Number fields are horizontal steppers, not native spinners.** Every `.ac-config-num` input renders inside a `.ac-num-stepper` wrapper that pins a **back (left) + forward (right) Lucide arrow INSIDE the field** at its two edges (replacing the browser's native up/down spin-buttons, which are stripped via `appearance` rules) and **centres the value between them** with `20px` of clearance each side so the arrows never overlap the number. Clicking an arrow steps the value by the field's `step`, clamped to its `min`/`max`, and fires the **same `input` + `change` events** the spinner did, so existing autosave / clamp listeners are untouched. The whole thing is driven by **one shared, idempotent, capture-phase document handler** (capture + `stopPropagation` so an arrow click never bubbles up to an ancestor row/ability toggle), wired lazily the first time a stepper is built. Both render paths live in `dom-utils.js`: the string builder `_renderSettingInput` (both ability tables) wraps inline, and the element builder **`_wrapNumberStepper(inputEl)`** wraps a created `<input>` (used by the agent **Config** tab, `tab-config.js`) — keeping all three number-field sites identical (SISTER-PANEL). The arrows use inline SVG (so they paint without a `lucide.createIcons` pass — the Config tab never runs one) and take their colour from `--fg-3` (→ `--accent` on hover), themed in both modes; a read-only/disabled field disables the arrows. Styling: `.ac-num-stepper` / `.ac-num-step` in `app3.css`.
- **Expandable rows** — wrap the row in `.ac-row` and give it an `.ac-ability-body`; clicking the row opens it to reveal **more detail and/or the configuration** (OAuth login, scopes, a dropdown, token fields, a longer explanation). Use this when a control or its detail is too big for the collapsed line — put the **control itself in the expanded body** (e.g. a settings dropdown with its hint) and keep the collapsed line to name + one-line summary.
- **Reorderable rows** — a row can carry a **drag handle** and be `draggable` so the list doubles as a drag-to-reorder list, while still showing each row's control (e.g. a visibility toggle). The flush list reads as one table; drag still works row-to-row. *Main Panel Pages / Admin Panel Pages — each row also carries an **icon button** (opens the shared Lucide picker) and an **inline rename** field beside the drag handle and the visibility toggle. That toggle is a **3-position `.ac-mp-tri`** (built to mirror the abilities `.ac-tri` look — grey knob = **Off**/hidden, amber knob = **Signed-in only**, accent knob on a filled track = **Always visible**): each click advances Off → Signed-in only → Always visible. It persists as a `visibility` override (`off`/`auth`/`all`; `all` clears it) on `data/config/{main,admin}-panel-pages.json` via the page-override API, and the header/sidebar builder (`header-build.js`) hides `off` pages from everyone and `auth` pages until the visitor has an auth token. A **locked** page (Admin Tools / Admin Configuration) can never be turned **off** — that would hide the only door to the app's config — so its tri stays interactive but **skips the leftmost off slot**, cycling only Signed-in only ⇄ Always visible (`_VIS_STATES_LOCKED`); the dead off zone is greyed via `.ac-mp-tri-nolock`, and both the catalog merge and the override route clamp/reject `off` for locked pages. The legacy boolean `hidden` still loads (== `off`) and migrates on next save.*
- **Locked / disabled / system rows** — a row can be non-interactive (locked, "always on", admin-only) and just render the state; keep it in the same list so the set stays visually unified.
- **Grouped rows (a group header + its members in the SAME list)** — when options fall into named groups, the group itself is an **expandable header row** (`.ac-row.ac-group` → `.ac-group-head` head + `.ac-group-body` members) *inside the one `.ac-list`* — never a nested bordered box. The members are plain `.ac-ability-row`s revealed on expand, sitting on a faintly recessed, indented surface so they read as children without becoming a second table. The group head carries a **3-position toggle** `.ac-tri` (Off · Mixed · On): clicking the left half turns every member off, the right half turns every member on, and the centre "mixed" detent is **derived** (set in code when members are partially on) — you reach it by toggling individual members, not by clicking it. The whole group/tri component lives in `app3.css` alongside the row component. *Agent Tools (Admin → Agent Settings) groups its 13 host abilities into Administrator / Core / Web (`_ABILITY_GROUPS`), **plus** the former integration categories as further group rows in the same table — Communication, Productivity, Social Media, Marketplaces, Payments, Developer, CRM (`_INTEGRATION_GROUPS`). The per-agent Abilities tab mirrors the host grouping — see `_AGENT_ABILITY_GROUPS` / `_buildAbilityGroupsGrid` in `agents.js`. Credential-backed members (Web Scraper, Browser Cookies, and every OAuth provider) keep their own config body; their group's tri-toggle only **reflects** how many are configured and bulk-**off** un-configures them — it can't bulk-enable an OAuth app that still needs its keys. Coming-soon members never count toward the active tri. **Every group row carries a same-size toggle for visual consistency:** a group with togglable ability members shows the active tri (a single-member group naturally reads as a plain on/off), while a group with none — placeholder-only, or credential/integration groups like Payments / Developer / CRM — shows an **inactive, greyed `.ac-tri.ac-tri-disabled`** rather than an empty gap. **The expand chevron sits to the LEFT of each row's icon** (`.ac-row-chevron--left`), on both group heads and member rows, after the indent. The admin table also adds a **hold-to-delete button as the LAST child of every row — group head and member alike — so they line up on one right edge**: the member button deletes that ability's files, the group-head button deletes the whole `plugins/abilities/<Group>/` folder (`DELETE /api/v1/abilities/{id}` and `/group/{gid}`). **Every config control in the ability tree confirms a save the SAME way — one shared indicator, centered ON TOP of the control (not in a side slot).** The flow is always: **a spinner overlaid on the control while the save is in flight (held a minimum ~400ms so it's always seen) → a green check ✓ once the backend confirms → fade**, or on failure **an orange warning triangle ⚠ over the control, a tiny 1–2 word warning popup floating just above it, AND the control reverts to its prior value**. It is driven by three shared helpers in `dom-utils.js`: `_saveOverlay(container)` lazily drops a `.ac-save-overlay` span (`position:absolute; inset:0`) into the control's container (made `position:relative`) and caches it on `container._saveOv`; `_markSaving(container)` shows the spinner overlay; `_flashSaveCheck(container, ok, errMsg)` settles it to ✓ / ⚠. **On the ⚠ failure path only,** `_flashSaveCheck` also pops a small themed label (`.ac-save-pop` — orange border + text on an elevated background, a little downward nub pointing at the triangle, centered above the control) so the failure is unmissable at a glance; the text is a short 1–2 word phrase derived by `_shortFailLabel(errMsg)` (default **"Not saved"**, or **"Not cleared"** for a failed Clear). The popup lifts-and-fades in with the triangle and is removed with it (`_clearSavePop`) when the overlay fades after ~2.6s; success shows only the green ✓ with no popup. The overlay (`.ac-save-overlay` + `.show`/`.ok`/`.err`, styled in `app3.css`) takes its colours from the design-system palette so it's theme-safe and matches the `.agents-autosave-check` tick the model + appearance tables use. The **container you pass is the control itself**: the toggle wrap (`.ac-ability-toggle-wrap`), the field's `.ac-config-control` slot, the permission/visibility `.ac-tri`, or a button — so the spinner/✓/⚠ sits exactly over what was changed. Applies to **every** persisted control: the enable toggle, the bulk group tri-toggle (per member), config/dropdown fields, the **Deny · Ask · Auto permission tri-toggle** (a per-tool `.ac-tri` mirroring the group toggle's look — left = **Deny**/off so the tool is removed from the agent entirely, middle = **Ask** for per-call confirmation, right = **Auto**/on; built by `_buildPermissionTri` in `dom-utils.js`, it replaced the old `.agents-tool-seg` Auto/Ask/Deny button strip), and the credentials Save/Clear buttons. The visibility **eye** is the one exception — it has no separate container, so it flashes the ✓/⚠ glyph **in place of the eye icon** itself, then repaints. `_flashStatusText` is kept ONLY for plain text messages that aren't save outcomes (e.g. a locked-on ability's "Cannot be deactivated"); the delete button is now **only** a delete button. **Two gotchas, both fixed:** (1) the admin config fields (`_buildConfigRows`) were rendered with **no change-to-save handler at all** — editing a setting did nothing and never persisted; a change→save handler is now wired (mirroring the agent panel). (2) the built rows carry their change-to-save listeners, so `_buildConfigRows` **returns the actual wired nodes** (`{nodes, note}`) and the caller **inserts those nodes** into the unified `.ac-list` — never re-serialized via `innerHTML`, which would silently drop every listener. **Backend (now wired):** the app-level save (admin scope) PUTs `/api/v1/abilities/{id}/config` and reads back via `GET /api/v1/abilities/{id}/config` (both admin-only, in `app/api/agents.py`) → `app/admin/ability_config.py` `set_ability_config`/`get_ability_config`, persisted to the repo-local `data/config/agent-abilities.json` under `ability_config.<id>` (NON-secret knobs only — secrets stay in the vault). Both routes call `ensure_bootstrapped` first so the config file **auto-seeds/self-heals** if it's missing (the file is also auto-created on any write — `_save` does `makedirs` + write), and `_buildConfigRows` now pre-fills the fields from the stored values via `_loadAbilityConfig` (admin renderer attaches the Bearer token through its local `_authFetch`). The per-agent config save already worked (green ✓). **App-level config is the app-wide DEFAULT (now wired):** the admin app-level `ability_config` store acts as the default that each agent's own per-agent config is layered on top of — `app/admin/ability_config.py` `effective_ability_config(id, per_agent)` merges the admin defaults UNDER the agent's own choices (built-in defaults ← admin app-level ← per-agent override, mirroring the global tool-permission defaults). The agent **runtime** consumes the merged result: `app/agent/context_control.py get_context_settings` (the compaction knobs) and `app/agent/ability_skills.py` (the declarative `config.bias` posture, e.g. `self_compaction_posture`). So an agent that has never overridden a knob inherits whatever the admin set in Agent Settings; an agent that saved its own value wins. Generic — any ability with a config-schema gets this layering for free. The two renderers are `ui/shared/js/admin-ability-table.js` and `ui/shared/js/agent-ability-table.js` (the agent table omits the delete buttons — it is the subset). **Expanding a member row is a single, flat reveal:** member rows sit close to the group's edge (a small ~20px indent, not a deep one); expanding shows that ability's **tools in full immediately** — there is no second collapsible "<Ability> tools" label/level any more. An ability's **config knobs and its tools now render as ONE continuous `.ac-list`**: every row (setting OR tool) is the SAME stacked `.ac-ability-row` — title + control inline, description on its own full-width line below — built by the shared `_buildSettingsRowsHtml` (config) / `_buildToolRow` (tools) and dropped into the single list from `_buildAbilitySettingsList` (config rows first, then tools, kept ordered by a comment anchor; the list self-prunes when empty). A tool's name stays monospace (`.ac-tool-name`) and its Deny·Ask·Auto tri + visibility eye sit in the same right-aligned `.ac-config-control` slot a setting's field/menu uses, so the two read as one table. This unified list is **NOT a bordered sub-table** — it keeps the `.ac-list` class only for its hairline row dividers, while CSS (`.ac-list.ac-config-settings`) strips the frame (border / radius / elevated fill / clip) so the rows flow **directly inside the expanded `.ac-ability-body`**, like the skill row, instead of nesting a box-in-a-box (the rejected look was "ability table -> ability -> tools/configs in a SUB-TABLE"). Its **left/right edges are evened up** so it isn't lopsided once unboxed: `#ac-abilities-compact .ac-ability-body` and `.conn-fields.ac-ability-body` pull the body's left padding back to the same `14px` the right uses (it was 20px base / 32px for a grouped member, to tuck settings under the ability name), and **on the agent card a `-18px` margin on the body cancels the member-card wrapper's left drag** (`.ac-group-body > .ac-row { padding-left:18px }`) so the body's dark background reaches both edges like the admin table's full-width body — net: dark area flush both sides, content inset ~14px both sides, skill row aligned. The shared **Appearance** theme editor is also `.ac-ability-body` but, having neither `.conn-fields` nor an `#ac-abilities-compact` ancestor, is excluded and keeps its own indent. Expanding also **un-clamps the description**: collapsed, `.ac-ability-desc` is line-clamped to 2 lines; the open row (admin `.ac-row-open`, agent/group `.ac-row.expanded`) removes the clamp so the **title row itself grows vertically** to show the full text — the description is never moved into a block below the title. **Loading entrance:** while the catalog (and, on the admin side, the global tool defaults) load, the container shows a centered spinner (`.ac-tree-loading` + spinning `.ac-tree-spinner`, built by the shared `_buildAbilityTreeLoader`); once the groups are built the spinner is cleared and they are revealed **one-by-one, each unfurling vertically from its top edge** with a ~70ms per-group stagger (shared `_staggerRevealGroups` applies an inline `animation-delay` + the `.ac-group-reveal` class, which it strips again on `animationend` so the search filter's `.expanded` toggling is unaffected; `@keyframes ac-group-reveal` + the `prefers-reduced-motion` opt-out live in `app3.css`). Both panels call the same loader/reveal helpers, so the entrance is identical.*

> **Sister panels — keep the two ability tables MIRRORED.** The admin **Agent Settings** table and the per-agent **Abilities tab** (agent card) are two renderings of the *same* table design. They must stay mirrored: any change to one side's look, structure, grouping, or toggle behaviour must be applied to the other in the same change. Both code sites carry the embedded banner **`SISTER-PANEL: AGENT-ABILITY-TABLE`** — grep it to jump between the admin side (`app-config.js`) and the agent-card side (`agents.js`). This is also called out as an always-on essential in `CLAUDE.md`.

**When NOT to use it:** a surface that's a genuine **form** — a set of free text/number fields the user fills in, with no per-option category structure — should stay a form, not be forced into rows. Likewise a panel that's really **one complex configurator** (many interdependent fields, live status, action buttons) is not a list of options. Rule of thumb: if you'd naturally describe it as "a list of things, each of which can be turned on / chosen / reordered," it's a compact table; if it's "a single thing with many fields," it isn't. (A hybrid is fine: *Remote Access* in Data Settings (below the Database card) is **one `.ac-list` table whose rows expand to hold the configurator** — Same network · Reach it from anywhere · On your phone — so the page reads as one table while each row's body is still a full form.)

### The standard config-page layout (App Settings is the reference)

Every admin config page (and any new config-style page) follows one shape, so the whole app reads as one system. App Settings is the worked example:

1. **No page-title header.** Don't open the section with an `.ac-section-header` (icon + `<h2>` + description) — the header tab carousel already names the page. The section is just a stack of groups.
2. **Subheadings are title-only.** A group is the plain-text `.ac-category-summary` (icon + title) — **no `.ac-category-desc`** explainer paragraph under it. (Functional warnings — e.g. the Remote Access security banner — are not subheading descriptions and may stay.)
3. **Every group body is one `.ac-list` table of uniform rows.** A row is the shared `.ac-ability-row` (icon + `.ac-ability-name` + one-line `.ac-ability-desc`) with its control in a right-aligned `.ac-config-control` slot. Put **simple controls inline on the right** — a `.conn-toggle` switch, an `.ac-input.ac-config-sel` dropdown, a number input — so every row bottoms out on the same right edge with the same `8px 14px` spacing. Reserve the **expandable** `.ac-row` + `.ac-ability-body` for genuine multi-field configurators (Remote Access, the per-theme palette), per the hybrid rule above. Don't hand-roll a bespoke toggle/slider — the unstyled `.ac-toggle`/`.ac-toggle-slider` markup that used to be in Startup & Boot was replaced with the shared switch.
   - **Row heights match across control types.** The inline `.ac-config-sel` dropdown is deliberately **compact** (`padding: 5px 10px; font-size: 12px` in `app3.css`) so a dropdown row sits at the *exact same height* as a toggle row — the default `.ac-input` (taller than the two-line label) made choice rows stand taller than on/off rows and broke the table rhythm. Keep new inline controls shorter than the label block.
   - **Each group is capped at 750px and centred** so rows stay a comfortable reading width instead of stretching the whole panel, and the heading's left edge lines up with the table below it. This is the reference width for the standard. **The cap is on the `.ac-category-summary`, the `.ac-category-body` *and* the `.ac-list`** (`max-width: 750px; width: 100%; margin: 0 auto` each) — **not** on the `.ac-category-group`, because the group is now `display:contents` for the sticky navigator (point 5), so it generates no box to cap. Capping the **body** (not just the list) matters so that anything a body holds *beside* the table — e.g. the Remote Access security banner — lines up to the same 750px instead of stretching the full section width. `width:100%` is required alongside `max-width` (the centring auto-margins cancel flex-stretch — see point 5).
4. **Sections that build their tables in JS ship a build gate.** If a section's `init()` rearranges static markup into formatted tables (Agent Settings builds the ability table, relocates integration cards, mounts the model table), the raw markup would flash as a half-formatted page before the build lands. Prevent it with the reusable **`.ac-section.is-building`** gate (in `app3.css`): the section template carries `is-building` on the `.ac-section` plus one `.ac-section-loader` child (a `.ac-tree-spinner` + label). From first paint every real child is hidden and only the centred spinner shows. Three gotchas the Agent Settings implementation already handles — copy them:
   - **Reveal only after structure AND the first data load.** Lifting the gate when the structure is built but before the integration/ability *data* has loaded flashes every toggle/badge in its default state for a beat (the "transient incorrect view"). So the reveal chain is `init()` → `_initIntegrations()` (build) → `.then(_loadIntegrations)` (first data snapshot) → `.finally(_clearBuildGate)`. The model table is exempt — it keeps its own correctly-formatted inline "Loading models…" state, so it doesn't block the reveal.
   - **`init()` owns the whole reveal — never gate it on `load()`.** `init()` (gate up) fires when the Admin tab initialises, but `load()` only fires when the App Config *view* is activated; those are different lifecycle events, so gating the reveal on `load()` can leave the spinner stuck. `load()` still re-fetches on later activations — an idempotent refresh over already-revealed tables.
   - **Clear the class directly — no `requestAnimationFrame`.** rAF callbacks are paused while the page isn't the foreground tab, which leaves the spinner stuck forever in a backgrounded view. The structure + data are already applied when `_clearBuildGate` runs, so a direct `classList.remove('is-building')` paints the finished tables in one frame with nothing half-built to hide.

   `init()` runs once on page load and the section DOM persists, so the gate clears exactly once and never re-sticks on a return visit. (App Settings has no JS-built tables, so it needs no gate.)
5. **Sticky section navigator (the advanced-scroll pattern — shared across config pages).** On an opted-in config page the section headings stay on screen the **whole** time you scroll: headings whose table you've scrolled past pin to the **top**, headings whose table is still below pin to the **bottom**, the one you're reading sits between them with its table, and every heading is **click-to-jump**. It's **shared, not per-page**: a page opts in with two changes — add the `ac-stickynav` class to its `<section class="ac-section">`, and call `initStickyNav('<section-suffix>')` from its module (the shared helper is `ui/admin-tools/app-config/sticky-nav.js`), usually both in `init()` and inside a `registerSectionHook(...)` so it re-measures every time the page is shown. **Live on:** App Settings, Agent Settings, Data Settings, and Features (the Features catalog emits the same `.ac-category-group` headings from `nav.js`). Single-heading pages (Users, Optimizer, Git) are deliberately **not** opted in — there's nothing to stack. (The former standalone Automation, Events and Monetization tabs were removed — Automation + Events folded into Agent Settings' Automation Engine, billing into the `plugins/billing` edition split.)
   - **CSS (`app3.css`, scoped `.ac-stickynav`).** A `position:sticky` element can only travel inside its own containing block, so a heading wrapped in its own `.ac-category-group` could only stick while that one group was on screen. The fix is `.ac-stickynav .ac-category-group { display: contents }` — that removes the group's box so the heading + its `.ac-category-body` become direct children of the whole section, making the heading's containing block the **entire page** (which is what lets it stay stuck across every other section). The summary then gets `position:sticky`, the 750px cap (point 3, also applied to the section header/banner so everything shares one width), a translucent **blurred** backing (`rgba(var(--bg-0-rgb), .82)` + `backdrop-filter: blur(10px)`) so rows scroll cleanly underneath while the living-glass page background still shows through, a `--border-soft` 1px shadow, and `--accent` colour on the `.ac-navh-active` (current) heading. **The headings themselves are SQUARE (`border-radius:0`)** — a rounded sticky *banner* leaves transparent triangles outside its own rounded border, and the table rows show sharply through them while you scroll. Instead, the **rounded look at the scroll-area edges comes from the SCROLLER**: `#app-config-content` has `border-radius: var(--r-lg)` + an overflow clip, so it clips **whatever sits at its top/bottom edge — a pinned heading OR a scrolling content row — to the rounded corner**, uniformly. For that clip to actually reach the content, the scroller's horizontal inset is a **margin, not padding** (padding would hold the content away from the rounded edge so nothing ever touches it; a margin shrinks the scroller box to where the content is). Headings stay square because the scroller does the rounding for them. (Earlier attempts — rounding the first/last heading's own outer corners — were reverted because the heading's rounded corner exposed the scrolling rows behind it; clipping at the scroller fixes that.) Section `gap` is set to `0` and the inter-section spacing moves to the summary's `margin-top:14px`.
   - **Collapsible pages — `.ac-collapsible`, NOT `<details>`.** `display:contents` on a native `<details>` breaks **both** its collapse *and* its flow layout (the details' content box drops out of the section's flex column, so open bodies overlap). So a collapsible group on a sticky-nav page is authored as a plain `<div class="ac-category-group ac-collapsible">` (the same element App Settings' always-open lists use, which flows correctly under `display:contents`) and is opened/closed via an `.ac-open` **class** — CSS `.ac-stickynav .ac-category-group.ac-collapsible:not(.ac-open) > .ac-category-body { display:none }` hides the body, and the chevron rotates on `.ac-open`. A group **without** `.ac-collapsible` stays always-open (App Settings' page lists; Agent Settings' Models / Agent Tools labels). Agent Settings was converted from `<details>`/`<summary>` to these divs; its search also switched from the dead native `.open` attribute to toggling `.ac-open`. **The storage/maintenance configs now live under Data Settings → Database** (the standalone "Data Management" tab was retired). Its group headings are always-open (no `.ac-collapsible`, no chevron) and pin top/bottom as you scroll. The configs are grouped under those headings — Application Data · Secrets & Encryption · Migration (Database group) — each heading over ONE shared `.ac-list` of expandable `.ac-row`s (the ability-table component, same hybrid pattern as Remote Access / the Automation Engine): a config collapses to a one-line row showing its live status (its `.ac-ability-status` badge) and expands in place to reveal its configurator. The two remaining Maintenance/Runtime rows (**Config Files** + **Stream Buffer**) moved to **App Settings → Advanced**. Rows are wired by `_wireDatabaseRows()` (data-settings.js) / `_wireBootRow()` (app-settings.js); every control id is preserved verbatim so `shared/js/storage.js` + `shared/js/data-management.js` drive them unchanged.
   - **JS (`sticky-nav.js`, `initStickyNav(id)`).** CSS can't know the stacked offsets, so JS measures each heading's height and writes inline `top` = combined height of the headings **above** it and `bottom` = combined height of those **below** it (so they pile up flush instead of overlapping); wires the click — **always-open** group → jump only; **`.ac-collapsible`** group → toggle `.ac-open` and jump when *opening* (the chosen "expand + jump" behaviour); and toggles `.ac-navh-active`. Gotchas baked in: **(a)** driven by `registerSectionHook(id, …)` — at `init()` the section is usually hidden so everything measures `0` and the recalc no-ops; the hook re-measures each time the page is shown (and `window resize` re-measures for font changes). Agent Settings additionally re-measures in the `.finally` after its **build gate** lifts, since the headings are hidden while `is-building`. **(b)** A sticky element pins at the scroller's **padding** edge, not its border edge, and `#app-config-content` has `padding: 28px 0 0` (the 20px horizontal inset is now a **margin** on the scroller, and the bottom padding is **0** so content reaches the rounded bottom edge — see the rounded-viewport note above). So the written offsets **subtract that vertical padding** (`top = heightsAbove − 28`, `bottom = heightsBelow − 0`; the helper reads `paddingBottom` live, so it tracks the value) so the top stack sits flush under the tabs and the bottom stack flush at the very bottom; the active-detection and click-jump add it back (`padTop + style.top`) so they read the engaged heading and land jumps flush. **(c)** The click-jump measures off the heading's (never-sticky) **body** to get its true flow position even when the heading itself is currently pinned. **(d)** Only **visible** headings join the stack — `_heads` filters `offsetParent === null`, so a page that hides groups at runtime (Agent Settings empties + hides its legacy integration categories once their cards relocate into the unified abilities table) doesn't get its offsets polluted by zero-height hidden headings.

**The on/off switch (`.conn-toggle` / `.conn-toggle-track`) now lives in the global `app3.css`** (moved out of the per-page `agents.css`, same precedent as the `.ac-config-*` widths), so config rows on pages that don't load `agents.css` (App Settings, Agent Settings) render the identical switch. Its active colour is still the legacy blue (`#1e3a6a` / `#7aa2f7`) rather than `var(--accent)` — a known app-wide quirk shared with every ability-table toggle; changing it is a separate, app-wide decision. The Main/Admin Panel Pages drag rows carry the **3-position `.ac-mp-tri`** visibility control, built to mirror the abilities-table `.ac-tri` (Off · Signed-in only · Always visible), so they read as the same tri component rather than a one-off switch.

**The per-agent Abilities table row now uses ONE 3-position visibility tri, not a [switch + eye] pair.** Each ability row in the agent ability table (`ui/shared/js/agent-ability-table.js`) carries a single `.ac-tri.ac-tri-vis` toggle — **Off · Discoverable · Visible** — built by the shared `_buildVisibilityTri()` in `dom-utils.js` and styled identically to the group tri it lines up under (same `.ac-tri` CSS: knob at 2/20/38px, grey/amber/accent; the visibility modes map onto the existing `off`/`mixed`/`on` detents). It orchestrates **both** backend writes: position 1 disables the ability (`onSave` false), positions 2/3 enable it (`onSave` true) and PUT its visibility mode (`discoverable` = the agent loads it on demand via `load_ability`; `visible` = its tools & skill are shown now). The control exposes `_apply(mode)` / `_mode()` so the group bulk tri drives each row (bulk-on → Visible, bulk-off → Off), and a locked-on safety ability rejects the Off detent (snaps back, reports "Cannot be deactivated"). This is **agent-only**: the admin ability table keeps its plain on/off switch + delete button, because visibility/discovery is tuned **per agent**, not at the app level — so the sister-panel rule does **not** require mirroring this tri into the admin table.

**The per-agent Abilities row also carries an "Available to" caller-access dropdown.** Beside the visibility tri (and only while the ability is enabled) each ability row in `agent-ability-table.js` shows a small `.ac-access-select` choosing **who may trigger that ability when chatting THIS agent**: **Everyone** (anyone, incl. not-signed-in anonymous guests — the default) · **Registered** (signed-in accounts only) · **Admins** (admins only). It is built by `_buildAccessSelect()` and saves to its own per-agent endpoint `PUT /api/v1/agents/{id}/abilities/{ability}/access` (`{user_id, level}`); a genuine restriction tints the control (`.ac-access-restricted`, accent border/fill) so a locked-down ability reads at a glance, and the wrap is excluded from the row's expand-click so picking a level never toggles the body open. Unlike visibility (a prompt-shaping hint), this is a **real security boundary enforced server-side at tool-assembly time** — `app/tools/loader.load_tools(gate_caller_access=True)` drops the gated ability through `app/agent/ability_access.filter_abilities_for_caller`, so its tools are never materialized for a caller below the level, and `app/agent/prompts.append_skills_section` strips the matching ability skill from that turn's prompt. Like the visibility tri and the config ceiling, it is **agent-only** (per-agent metadata `ability_access`, absent = everyone) — the admin global ability table has **no** equivalent control, so the sister-panel rule does **not** require an admin-side mirror. (Style: `.ac-access-wrap` / `.ac-access-select` in `app3.css`, design-system tokens only.)

**Destructive confirmations use the shared in-app hazard panel, NOT the native `confirm()` popup.** For a "are you sure?" on a destructive or important action, call **`hazardConfirm({title, message, confirmLabel, cancelLabel, tone})`** from `ui/shared/js/confirm-dialog.js` (returns a `Promise<boolean>`) instead of the browser's `confirm()` — the native dialog looks foreign and can't be themed. The shared panel is a centred, design-system-themed notification card with a **hazard badge** (an inline `alert-triangle` SVG so it paints with no Lucide pass), a title + message, and Cancel / Confirm buttons; `tone: 'warning'` (amber) or `'danger'` (red) recolours the badge + confirm button. Esc / backdrop-click / Cancel resolve `false`; focus starts on Cancel and Enter is **not** a global confirm, so a stray keypress can't fire a hazard. Style lives in `app3.css` under **`SHARED-HAZARD-CONFIRM`** (`.wa-confirm-*`), tokens only, theme-safe. First adopted by the encryption master + per-database toggles (`storage.js`, now under Data Settings → Database); the older inline `confirm()` calls elsewhere in `storage.js` (expert field-encryption tools, backend switches) are candidates to migrate to it.

**The per-agent Abilities tab loads PROGRESSIVELY (four staged steps) — agent-tab only.** The agent tab needs a **second, per-agent** `/connections` fetch (its enable + visibility state) on top of the shared catalog, and an agent can have many abilities — so `agent-ability-table.js`'s `build()` no longer waits for everything before painting. The stages: **(1)** a spinner shows instantly — the caller (`tab-abilities.js`) builds the panel skeleton + the table's `_buildAbilityTreeLoader()` **synchronously**, before any `await`, so the panel is never blank (the old bug: the "Loading…" line was only set *after* the catalog `await`, so a tab click showed nothing); **(2)** the **group heads** render from the catalog alone (which members belong is decided from the catalog's resolved `enabled`, so no per-agent data is needed and there's no flash), each with a **spinner where its bulk toggle will go** (`_buildGroupTriSpinner` → `.ac-tri.ac-tri-loading`, same 54×20 footprint so nothing shifts); **(3)** the `/connections` fetch — kicked off in **parallel** with step 2 — lands and each group's spinner is swapped for the real Off·Mixed·On tri, with empty groups hidden; **(4)** a group's **member cards** are built only when it is **first expanded** (`_ensureGroupBuilt`, a cached promise), and each ability's heavy body (tools / skill / config / schema) is *still* built lazily inside the card on its own expand. ## Lucide icons & icon buttons — the only correct pattern

The app pins **Lucide 0.469.0** (loaded as a global in `index.html`). This version has two traps you must design around: `createIcons({ nodes: [...] })` **ignores the `nodes` filter and rescans the whole document**, and every `<svg>` it generates **keeps its `data-lucide` attribute** (it just also gains the class `lucide`). So any `createIcons()` call re-builds *every* icon on the page into a brand-new DOM node. A central auto-renderer in `ui/shared/js/icons.js` already manages this safely — getting it wrong reintroduces the infinite re-render loop that silently broke the chat **+** button (a button whose whole hit area is an icon never fires `click` if its node is swapped between press and release).

**Rules — follow these everywhere you use a Lucide icon:**

1. **Emit a placeholder, let the central renderer convert it.** In string/innerHTML contexts use the `icon('name', { size })` helper from `ui/shared/js/icons.js`; when building DOM, create an `<i>` and `setAttribute('data-lucide', name)`. Insert it into the DOM and the `MutationObserver` in `icons.js` renders it on the next frame. That observer renders **only** unprocessed placeholders (`[data-lucide]:not(.lucide)`).

2. **Never run a bare `lucide.createIcons()`**, and never call it from your own `MutationObserver` / on every DOM mutation / on an interval. A bare call rebuilds all 150+ icons and, if fired from an observer, self-feeds into a once-per-frame loop. If you must render a specific subtree explicitly, scope it: `lucide.createIcons({ nodes: Array.from(host.querySelectorAll('[data-lucide]:not(.lucide)')) })` (the `:not(.lucide)` guard is mandatory and is the convention used throughout `files.js`).

3. **To change an already-rendered icon's glyph in place, strip the `.lucide` class first**, then re-render that node — otherwise it's treated as "already done" and nothing happens. Plain `el.setAttribute('data-lucide', 'newname')` on a rendered `<svg>` is a **no-op**. Copy the existing pattern: `_setActionIcon` in `chat-bubble-actions.js` (set attr → `classList.remove('lucide')` → `createIcons({ nodes: [el] })`). Prefer instead to **replace the whole icon by re-inserting a fresh `<i data-lucide>` placeholder** when the surrounding element is rebuilt anyway.

4. **Bind click handlers to the button element, never to the inner icon node.** Icon `<svg>`/`<path>` nodes can be replaced by a render pass, so a listener on them (or a cached reference to them) is unreliable. Attach to the `<button>` directly (like the chevron/delete buttons) or delegate with `e.target.closest('#the-button-id')` on a document capture listener (like `#session-new`). The button element itself persists across icon swaps.

5. **Use valid Lucide 0.469 icon names.** An unknown name (e.g. `users-cog` instead of `user-cog`) leaves an unrendered `<i>` and spams the console with `icon name was not found`. When unsure, verify the name exists in this version before shipping.

## Clipboard — Ctrl/Cmd C / X / V / A work everywhere (don't re-implement)

`ui/shared/js/clipboard.js` installs ONE document-level capture-phase key handler (`initClipboard()`, called once in `main.js` right after `bindDom()`). For the four clipboard shortcuts it performs the operation itself — copy/cut the selection (from an input/textarea value, a contenteditable, or any page text selection), paste at the caret, select-all within a field — and stops anything downstream from swallowing or cancelling the key. This is why copy/paste works in every panel without each panel wiring it.

**Rules:**

1. **Don't add per-field copy/paste keydown handlers** for the basic shortcuts — the global net already covers them. A panel-level `keydown` that `preventDefault`s on Ctrl+C/X/V isn't needed and risks fighting the net.
2. **For copy *buttons*, use `copyText(text)` from `clipboard.js`** (not `navigator.clipboard.writeText` directly). It falls back to the legacy `execCommand` path so copy buttons also work over a non-secure `http://<ip>` LAN address, where the async Clipboard API is unavailable.
3. **Terminals are intentionally excluded.** The net bails out for anything inside `.xterm` / `.terminal` / `.terminal-frame` / `[data-terminal]` so Ctrl+C still sends an interrupt and xterm keeps its own copy/paste. If you add a new terminal surface, give it one of those classes (or `data-terminal`) so it's excluded too.
4. **Cross-document iframes are out of scope** (their key events never reach the parent); a new editable iframe would need its own handling inside that document. **First-class genui** (`ui/main-panel/genui`) are NOT iframes — they render in a shadow root in this document, so their key events DO reach the net, but retarget to the genui host (not the inner field), so the net bails and native clipboard takes over. (Note the flip side: app-wide keyboard shortcuts bound at the document level also see the retargeted host, not the genui's inner input — guard global shortcuts with an `e.target` check if a genui field shouldn't trigger them.)

## Recycling-bin toolbar (Agents page, mirrored to Sessions)

The Agents page header (`ui/main-panel/agents/agents.html` → `#agents-toolbar`, wired in `ui/main-panel/agents/js/agents.js`) carries a right-side action set that drives a soft-delete **recycling bin**: per-square **checkboxes** (top-right of every *custom* agent tile — templates and the "New Agent" tile get none) plus **Select all / Deselect all / Trash**. The bin is a **view-swap inside the same Agents tab**, NOT a new nav tab — driven entirely by the header:

- **Trash with squares checked** → two-click hazard confirm (the shared `delete-control.js` affordance) → moves the checked agents to the bin (`DELETE /api/v1/agents/{id}`, soft).
- **Trash with nothing checked** → opens the bin view: the title flips to **"Back to Agents"** (click it or the back arrow to return), a **Restore** button appears, the "New Agent" tile is hidden, and the Trash button now **permanently** deletes the checked agents (`&permanent=true`).
- **Restore** (bin only) → `POST /api/v1/agents/{id}/restore`, back to the Agents page.

State lives in two module vars in `agents.js` (`_binView`, `_selectedIds`); `_updateBinToolbar()` keeps the header (title, which buttons show, enabled/disabled) in sync after every render. Styling follows the **dark + light** rule (explicit `body.light-mode` overrides in `agents.css`, no hard-coded single-theme colour). 

**HARMONY — keep Agents and Sessions bins mirrored.** The same toolbar/bin pattern is intended for the sessions page; the markup carries a `HARMONY-AGENTS-BIN` marker that pairs with `HARMONY-SESSIONS-BIN`. Any change to the toolbar layout, bin states, or right-side actions on one side must be copied to the other. (Chat-header session delete already soft-recycles via the shared `status` column; the dedicated per-session restore UI is a future sessions page.)
