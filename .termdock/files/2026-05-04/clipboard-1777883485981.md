Task

 Add a live pipeline visualizer to webAgent. A new "Loop" button in the UI opens a top-down flow   
 chart that shows every internal step of the agent as it happens — not just LLM tool calls, but    
 the full Python execution pipeline: memory search, prompt building, tool loading, validation, DB  
 writes, skill tracking, guardrails, turn limits, and everything in between.

 ────────────────────────────────────────────────────────────────────────────────

 Architecture Summary

 webAgent is a Python FastAPI server. The agent loop is in app/agent/streaming_loop.py (WebSocket  
 streaming) and app/agent/loop.py (HTTP chat). Both use an async agent loop: load tools from DB →  
 build system prompt → call LLM → stream tokens → execute tool calls → save to DB → repeat until   
 no more tool calls or max turns.

 Current WebSocket at /api/v1/agent/ws already emits events: stream, tool_call, tool_result,       
 response, error. The UI at ui/js/ already renders these in a "Stream" tab and a chat panel. The   
 front end is vanilla JavaScript (ES modules), no framework.

 DB is SQLite (local_webagent.db) with tables: interactions, context_documents, tools, skills,     
 skill_executions, skill_feedback, memories, memory_chunks, memory_links, memory_timeline.

 The server is multi-tenant — all queries scoped by user_id.

 Phase 2 — Agent Loop (streaming_loop.py, inside the turn loop):

 ```python
   # At start of each turn
   yield {"type": "pipeline", "level": "pipeline",
          "step": "turn_start", "turn": turn_count, "max_turns": max_turns}

   # After loading tools
   yield {"type": "pipeline", "level": "pipeline",
          "step": "load_tools", "count": len(tools),
          "names": list(tools.keys()),
          "duration_ms": load_duration}

   # After building tool definitions for LLM
   yield {"type": "pipeline", "level": "pipeline",
          "step": "tool_defs_built", "count": len(tool_definitions)}

   yield {"type": "pipeline", "level": "pipeline",
          "step": "llm_call_start", "model": model_name,
          "message_count": len(messages),
          "turn": turn_count}

   # After LLM call completes (before processing tool calls)
   yield {"type": "pipeline", "level": "pipeline",
          "step": "llm_call_end", "duration_ms": duration_ms,
          "input_tokens": input_tokens, "output_tokens": output_tokens,
          "has_tool_calls": bool(tool_calls_data)}

   # Before validation
   yield {"type": "pipeline", "level": "pipeline",
          "step": "validate_start", "tool_count": len(tool_calls_data or [])}

   # Per-tool validation result
   yield {"type": "pipeline", "level": "pipeline",
          "step": "validate_result", "tool": tool_name,
          "passed": validation_error is None,
          "error": str(validation_error) if validation_error else None}

   # Before concurrent execution
   yield {"type": "pipeline", "level": "pipeline",
          "step": "execute_batch_start", "tool_count": len(valid_calls),
          "tools": [name for _, _, name, _ in valid_calls]}

   # Per-tool execution start
   yield {"type": "pipeline", "level": "pipeline",
          "step": "execute_start", "tool": tool_name}

   # Per-tool execution end (ADD to existing tool_result pipeline near the skill track section)    
   yield {"type": "pipeline", "level": "pipeline",
          "step": "execute_end", "tool": tool_name,
          "duration_ms": result["duration_ms"],
          "success": success}

   # After turn check
   yield {"type": "pipeline", "level": "pipeline",
          "step": "check_continue", "turn": turn_count,
          "max_turns": max_turns, "will_continue": turn_count < max_turns}
 ```

 Part 4: Key Design Rules

 1. Text only. No canvas, no SVG, no D3, no heavy libraries. Pure DOM nodes with CSS styling.      
 2. Live append. Nodes appear as events arrive. No page reload. No polling.
 3. No scrolling jank. When auto-scroll is on, use scrollIntoView({ behavior: "smooth" }) on each  
 new node.
 4. Resilient. If WebSocket disconnects, show a "reconnecting..." banner. When it reconnects,      
 continue from the last event.
 5. Backwards compatible. Existing WebSocket clients (the Stream tab, the chat UI) must continue   
 working. The level field is additive — old clients ignore unknown fields.
 6. Concurrent tool rendering. When asyncio.gather runs N tools at once, the nodes appear
 side-by-side (flexbox row) connected by branch lines (CSS borders/pseudo-elements). When all      
 resolve, a convergence line brings them back to a single vertical flow.
 7. Guardrail visualization. When a tool is blocked, show a red guardrail node. When confirmed,    
 show a green confirmed node immediately after. The tool node appears only after confirmation. If  
 blocked without confirmation, show tool as "BLOCKED" without executing it.
 8. Max turns. When the loop hits max turns, show a distinct orange/yellow milestone node: "⚠️ Max  
 turns (10) reached. Agent stopping."
 9. Multi-tenant isolation. The visualizer connects to a specific user's WebSocket. If user_id     
 changes, disconnect and reconnect with the new user's session.

 Part 6: Non-Streaming (HTTP Chat) Support

 The /api/v1/chat POST endpoint calls run_agent_loop() which is not a generator. To support the    
 visualizer for this endpoint:

 WebSocket, it sends {"mode": "http_chat", "user_id": "...", "session_id": "..."}. The server

 run_agent_loop with a callback that yields events.

 Option B: Add a callback parameter to run_agent_loop that receives pipeline events. The chat      
 endpoint creates a queue and the visualizer polls or subscribes to it.

 Implement Option A. The WebSocket handler in app/api/agent.py already supports receiving
 messages. Add a mode switch:

 ```python
   if msg.get("mode") == "http_chat":
       # Don't start agent loop. Subscribe as a listener for chat endpoint events.
       await register_visualizer_listener(websocket, msg["user_id"], msg["session_id"])
 ```

 The chat endpoint then pushes events to all registered visualizer listeners for that session.
